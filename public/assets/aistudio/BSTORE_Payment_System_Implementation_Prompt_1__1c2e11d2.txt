BSTORE — Enterprise-Grade Payment System
Complete Implementation Specification for Google AI Studio

You are working on an existing production-oriented Android application named BSTORE, built with Kotlin, Jetpack Compose and Firebase.

Your task is to inspect, architect, implement, secure, test and document a complete payment management system for BSTORE.

This must be a real, functional implementation integrated into the existing application — not a mockup, prototype or isolated demonstration.

The system must support:
1. Bank transfer to a selected bank account:
   - Bank of Georgia (საქართველოს ბანკი)
   - TBC Bank (თიბისი ბანკი)
2. Cash on Delivery (COD) / payment upon receiving the order.

The architecture must also support adding additional banks in the future without redesigning the payment system.

All customer-facing UI and text must be in natural Georgian.

PART 2 — PAYMENT SYSTEM ARCHITECTURE

2.1 Core payment methods

Implement two payment methods.

Method A: Bank Transfer

The customer pays manually by transferring money to one of the BSTORE-configured bank accounts.

Supported banks initially:
- საქართველოს ბანკი
- თიბისი ბანკი

The architecture must support additional banks in the future.

This is a manual bank transfer system. Do not describe it as an automatic bank integration.
Do not pretend that the application can detect incoming bank transactions automatically.
Do not implement fake transaction verification.

Method B: Cash on Delivery

The customer pays when receiving the ordered goods.

Do not assume that courier card payments are available.
Do not promise courier cash collection unless the existing delivery arrangement supports it.
The admin must record COD collection only after the money has actually been received.

2.2 Keep payment and order fulfillment separate

Payment status and order status must be separate concepts.

For example:
- An order can be confirmed but still unpaid.
- An order can be paid but not yet shipped.
- An order can be delivered but COD collection still needs to be recorded, if that is the actual business situation.

Preserve the existing order lifecycle and integrate payment state without replacing existing order statuses.

Never infer that an order is paid merely because it was created, confirmed or delivered.

2.3 Payment status model

Use these recommended payment statuses, adapting existing compatible values if necessary:
- `pending` — bank transfer awaiting manual confirmation.
- `awaiting_collection` — COD payment not yet collected.
- `paid` — payment received and confirmed.
- `failed` — payment could not be completed, where applicable.
- `cancelled` — payment cancelled.
- `expired` — payment instructions expired, only if an explicit and tested expiration policy is implemented.
- `refunded` — money has actually been refunded, if refund tracking is supported.

Do not automatically expire orders without a defined business rule.
Do not automatically mark a payment as refunded merely because an order was cancelled.
Use consistent status transitions and validate every transition on the trusted backend.

PART 3 — MULTI-BANK TRANSFER SYSTEM

3.1 Bank account management

Create a scalable, admin-managed bank account configuration.

Initially support:
1. Bank of Georgia.
2. TBC Bank.

Each bank account must be independently configurable.

Required fields:
- Unique bank account ID.
- Bank identifier, such as `bog` or `tbc`.
- Bank display name.
- Bank logo or appropriate existing visual asset, if available.
- Account recipient name.
- IBAN.
- Optional account description.
- Optional payment instructions.
- Enabled/disabled state.
- Display order.
- Creation timestamp.
- Last updated timestamp.
- Admin UID responsible for the latest change.

Do not hardcode the actual IBANs or recipient details.
Do not invent account numbers, recipient names or bank information.
The administrator must enter the real bank information through the admin panel.

The system must support multiple accounts if necessary, including multiple accounts belonging to the same bank in the future.

Never assume the account holder and legal seller are the same person. Store the actual account recipient information supplied by the administrator.

3.2 Customer bank selection flow

Implement the following complete customer experience:

1. Customer adds products to the cart.
2. Customer proceeds to checkout.
3. Customer selects bank transfer.
4. Customer confirms the order.
5. The order is securely created.
6. The application displays available enabled bank accounts.
7. Customer chooses:
   - საქართველოს ბანკი
   - თიბისი ბანკი
8. The application securely retrieves the selected account instructions.
9. The customer sees a dedicated payment instructions screen.

The customer should choose the destination bank account, not necessarily the bank from which they are sending money. Make this distinction clear in the UI.

If only one bank account is enabled, it is acceptable to display that account directly, while keeping the architecture ready for multiple accounts.

If no bank account is enabled, do not allow the customer to proceed with bank transfer. Show an appropriate message and offer the other available payment method.

3.3 Dedicated payment instructions screen

Create a polished and trustworthy screen.

Display:
- Order number.
- Exact order amount.
- Currency: GEL.
- Selected bank name.
- Recipient name.
- IBAN.
- Payment reference or order number.
- Payment instructions.
- Payment status.
- A clear explanation that the payment will be confirmed after the actual bank transfer is verified by BSTORE.

Include:
- Copy IBAN button.
- Copy order/reference number button.
- Clear visual feedback after copying.
- Back-to-order-details navigation.
- Loading and error states.

Use the selected bank's logo only if a valid asset is available. Do not invent or use misleading bank branding.

The bank details must not be permanently displayed in the public app or exposed before a valid order is created.

The customer must only retrieve instructions for their own eligible order.

3.4 Payment reference

Generate a unique, human-readable payment reference based on the order identifier.

The reference must be stable and associated with the order.

Tell the customer to include it in the transfer description where supported.

Never use a customer-supplied reference as proof of payment.

The admin must verify the actual incoming bank transaction.

3.5 Bank selection persistence

Once the customer selects a destination bank:
- Save the selected bank account ID and relevant non-sensitive snapshot to the order.
- Preserve the exact recipient and IBAN details associated with that order.
- Do not silently change an existing order's payment destination if the admin later edits bank configuration.
- Existing orders must continue displaying the original payment instructions associated with them, subject to secure access rules.

If an account is disabled after an order has already been created, do not corrupt the existing order.

Define an appropriate policy for pending orders associated with disabled accounts and communicate it clearly to the admin.

PART 4 — CASH ON DELIVERY

Implement a complete COD flow.

Customer:
1. Selects cash on delivery.
2. Reviews the order amount and delivery information.
3. Confirms the order.
4. Sees a clear explanation that payment is due upon receiving the goods.
5. Can see COD as the selected payment method in order details.

The payment status initially becomes `awaiting_collection`.

Admin:
- Sees COD orders awaiting collection.
- Opens order details.
- Confirms collection only after receiving the actual money.
- Can enter an optional internal note.
- Sees who recorded collection and when.

After successful backend confirmation, payment status becomes `paid`.

The customer must never be able to confirm their own COD payment.

Do not assume the courier has received or transferred the money until that has actually been confirmed.

- Retrieving eligible bank instructions.

- Admin confirmation of COD collection.

6.3 Security requirements

Every operation must validate the relevant permissions and data.

For customer requests:
- Require Firebase Authentication.
- Verify order ownership.
- Verify that the order exists.
- Verify payment method.
- Verify order/payment state.
- Return only the data required by the customer.

For administrator requests:
- Require Firebase Authentication.
- Verify existing admin authorization or appropriate Custom Claims.
- Do not trust a client-provided role.
- Verify that the operation is permitted.
- Record the actual authenticated admin UID.

Customers must never be able to:
- Change payment status to `paid`.
- Confirm their own COD collection.
- Change the order amount.
- Change the payment method after an irreversible payment state transition.
- Modify the bank configuration.
- Access another customer's order or bank instructions.
- Write or modify audit history.
- Pretend to be an administrator.

Never trust amounts, permissions or payment statuses supplied by the client without backend validation.

Calculate or verify the payable amount using trusted order data.

Use Firestore transactions where appropriate.
Make privileged operations idempotent.
Prevent duplicate confirmations, race conditions and invalid state transitions.

6.4 Firestore security rules

Review all existing rules before changing them.
Do not replace the entire ruleset with broad permissive rules.
Preserve access to existing working application features.

Ensure:
- Public users cannot read private bank configuration.
- Customers can only read their own orders.
- Customers cannot update privileged payment fields.
- Customers cannot write audit events.
- Only authorized administrators can manage bank configuration.
- Payment confirmation is performed by trusted backend operations.
- Existing valid catalog and application reads continue working.

Test direct Firestore access attempts, not just UI restrictions.
Hiding a button in the UI is not security.
